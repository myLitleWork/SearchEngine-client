# Handoff: актуальная предрелизная оценка SearchClient

Дата последней перепроверки: 2026-08-16.
Дата серии правок: 2026-08-16 (блокер 1 B; 3+4 A+A; 5 A; 6 A; FireDAC B+skip;
N2Click A; P1/P2 A…; rare: file no-replace, 1GiB, InitDbgDS; admin984 B risk).

## Итог

Проект пока не следует считать готовым к каноническому Release. Причина — не
гипотетические совпадения, а оставшиеся в активном коде пути, где пользователь
может получить неполный результат, потерять прежний файл либо увидеть сообщение
об успехе после частичной операции.

Это статическая перепроверка. Сборка, запуск клиента, сетевые операции и работа
с базами не выполнялись в текущих сериях 2026-08-16 (по запросу владельца
сборка не запускалась). Документированный controlled-server smoke-test
по-прежнему помечен как невыполненный в `docs/CONTROLLED_SMOKE_TEST.md`.

## Как работать по этому handoff

Идём строго по одному шагу. Перед каждой серией:

1. ещё раз показываем проблему на текущем коде;
2. обсуждаем варианты и выбираем один;
3. только после явного согласования меняем оговорённые функции;
4. проверяем diff и выполняем соразмерную проверку;
5. отмечаем в этом handoff фактический результат и только потом открываем
   следующий шаг.

Пометка **Рекомендуемый** означает лучший баланс сохранности данных,
предсказуемого поведения и объёма изменений. Это предложение для согласования,
а не разрешение начинать правки автоматически.

## Подтверждённые блокеры

### 1. Результаты поиска сохраняются не как единая достоверная операция — устранено (вариант B)

Было: после сбоя `StartTransaction` вставки продолжались без явной частичности;
ошибка строки показывалась модально, остальные коммитились; статус брал
`telegi.size()`; `rel` писался как `int`.

Как исправлено (согласован B): частичный набор допускается; счётчики
успех/отказ; `rel` = `ftFloat`; расшифровка ошибок и предупреждений дат — в
`rchEdt`; статус показывает фактически сохранённое число; при автозагрузке
единственной телеграммы отчёт не затирается (`applyRchEdtText`).

### 2. Сохранение базы описи сначала уничтожает старый результат — устранено

Было: `btnSaveOpisBaseClick` удалял существующий `<год>.db` до записи,
`fwrite(&str[0], ...)` не обрабатывал пустой ответ и не проверял
`fwrite`/`fclose`, после этого показывалось «База успешно сохранена».

Как исправлено: выбран согласованный вариант безопасной атомарной замены.
`UserFileReplace::WriteReplacing` пишет уникальный sibling `_SCX-*.tmp` в том
же каталоге, делает `FlushFileBuffers`/close и проверку размера, затем
публикует одним переименованием на том же томе (`MoveFileExW` для нового файла,
`ReplaceFileW` с внутренним `_SCB-*.bak` при замене). При сбое удаляется только
собственный временный файл; старая база остаётся. Пустой payload отклоняется
до публикации. Пользователя не спрашивают.

Это локальный эквивалент Otpravka `WriteUserDataReplacing`, не порт `SafeIo`.
Префиксы `_SCX-`/`_SCB-` намеренно не совпадают с `_SPF-`/`_SPB-`.

### 3. Обычные файлы и ZIP ещё могут дать ложный успех — устранено (A+A с п.4)

Было: совпадение размера = «уже существует»; `ExtZip` глотал ошибки элемента;
`SaveFileIsh` всегда писал полный успех распаковки.

Как исправлено: `ClientFilePublish` + статусы распаковки; размер больше не
доказательство содержимого; частичная распаковка явно логируется.

### 4. Серверные пути вложений могут выйти из выбранного каталога — устранено (A)

Было: `Message::saveToDirectory` и целевые имена ZIP без containment.

Как исправлено: `ResolveUnderBase` (подкаталоги допустимы; `..`/absolute/rooted
запрещены) в Message и ExtZip.

### 5. Миграция старого `Res.db3` может зафиксироваться в частичном состоянии — устранено (A)

Было: целевые БД создавались на месте; повтор только при отсутствии `Settings.db3`.

Как исправлено: работа во `_SCM-set-`/`_SCM-res-` sibling, проверка таблиц и
`COUNT(*)`, публикация SearchRes затем Settings, удаление `Res.db3` последним.
Повтор, пока legacy на месте и Settings неполный относительно `Res.db3`.

### 6. Фоновые операции и закрытие формы не имеют общего lifetime-контракта — устранено (A)

Устранено для поиска, загрузки на отправку, текста, пути/ПДТВ, входа/выхода и
описи: live-token, inflight до UI-callback, FormClose ждёт; фреймы `BindLife` +
`detached_` в `Detach`.

Остаточный риск: фоновое пакетное сохранение файлов по-прежнему через
`saveRunning` (отдельный запрет закрытия); `FrameAttachments::FillDbg` синхронный.
