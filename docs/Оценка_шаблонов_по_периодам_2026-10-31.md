## Варианты реализации

### 1. Настройка через существующие SQL-шаблоны

Создать группы «Входящие» и «Исходящие» с четырьмя сохранёнными SQL-условиями. SQLite умеет вычислять текущую дату при выполнении запроса. Значит, для динамического «сегодня» изменение Request или протокола принципиально не требуется.

Например, **только при формате DData `дд.мм.гггг`**: SQL включён, поле SQL, тип Вх., текст `DData = strftime('%d.%m.%Y', 'now', 'localtime')`. Для вчера добавить модификатор `'-1 day'`. Сохранять следует само выражение, а не сегодняшнюю буквальную дату. Вводить полный SELECT, собственный ORDER BY или LIMIT в этом варианте не требуется: их формирует текущий путь клиента.

Для диапазонов нужно преобразовать текст DData в ключ `гггг-мм-дд`: `substr(DData,7,4)||'-'||substr(DData,4,2)||'-'||substr(DData,1,2)`. Сравнивать исходные строки `дд.мм.гггг` через BETWEEN неправильно на границах месяцев и лет. SQL-функция `date(DData)` без преобразования этого формата также не является достаточным решением.

Ограничения: формат рабочих данных не проверен; время берётся на каждом сервере; лимит остаётся общим параметром окна; порядок пунктов алфавитный. Пользовательские Templates.json этим анализом не редактировались.

### 2. Рекомендуемое расширение клиента

Сохранить существующую модель групп и добавить понятный выбор относительного периода. Предложенный набор для каждой группы:

| Пункт | Границы по календарной дате регистрации |
|---|---|
| Сегодня | Текущий календарный день |
| Вчера | Предыдущий календарный день |
| Последние 7 дней | Сегодня и шесть предыдущих дней |
| Последние 30 дней | Сегодня и двадцать девять предыдущих дней |
| Текущий месяц — дополнительно | С первого числа текущего месяца по сегодня |

При необходимости предыдущего календарного месяца следует добавить отдельный пункт «Прошлый месяц». Подпись «За месяц» без уточнения не задаёт однозначных границ.

Предлагаемые изменения:

1. Необязательные поля Request: тип периода, поле даты, лимит и режим сортировки. Старые файлы читать с прежними значениями по умолчанию: текущий `FROM_JSON` использует обязательный `.at()`, поэтому новые поля нельзя просто добавить тем же способом без fallback.
2. Пересчитывать период при каждом запуске поиска. Рекомендуемый источник календарной даты — ПК клиента, один раз на весь поиск, с одинаковыми вычисленными границами для всех серверов. Показать пользователю фактический интервал. Если нужен общий организационный часовой пояс, сделать это отдельным явным правилом.
3. По умолчанию использовать «Дата вх./исх.» / DData. Выбор даты подписи при необходимости сделать отдельным параметром. Это выборка по учётной дате, а не по моменту появления файла в индексе.
4. Предлагать готовые группы без перезаписи пользовательских шаблонов. Хранить явный порядок или выводить готовые пункты упорядоченным списком; не рассчитывать на текущий std::map.
5. Применять режим SQL и зависимые настройки единым путём; сохранять ожидаемое поведение одного и двойного щелчка. Проверить вариант, когда текущий режим до выбора шаблона был текстовым.
6. Для этого сценария использовать сортировку таблицы по дате регистрации и номеру, согласованную с выбранным периодом; нынешний default относится к дате подписи.

Эти изменения фильтрации можно передать существующими SQL-командами, без нового wire-протокола. Сохранённая серверная группа по умолчанию остаётся выбранной пользователем. При переходе через 1 января в ней должны быть доступны службы обоих нужных лет; шаблон сам не подключает отсутствующий год.

### 3. Отдельно: гарантированно самые последние N

Текущее `ORDER BY index DESC` применяется внутри каждой базы. Сервер сначала собирает строки из первой базы и может достичь лимита до просмотра следующих. Сортировка уже полученных строк в клиенте не возвращает пропущенные более новые записи. Несколько серверов имеют независимые лимиты; N=30 на двух серверах может дать до 60 строк.

Поэтому для обещания «самые последние 100 по дате среди всех выбранных источников» нужны отдельная серверная выборка с согласованным порядком по нормализованной дате и номеру, затем объединение и общий лимит в клиенте. Потребуется определить поведение одинаковых карточек из оперативной/месячной базы и tie-break для разных источников. Это отдельная доработка от простых шаблонов по периоду. Конкретный формат запроса и необходимость расширения протокола следует выбирать при проектировании; сама идея периодов нового протокола не требует.
